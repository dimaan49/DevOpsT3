# AuctionHub

Программа для проведения интернет-аукционов.

## Назначение

Клиент-серверное приложение для проведения открытых английских аукционов.
Поддерживает учёт аукционов, лотов, продавцов, покупателей и фактов продажи.

## Стек

- C++17
- Qt 6 (Core, Network, Sql, HttpServer)
- PostgreSQL
- CMake + Ninja
- easylogging++ — для логирования
- Catch2 (планируется)
- clang-format, clang-tidy

## Структура проекта

```
.
├── CMakeLists.txt
├── Makefile
├── .env.example
├── docs/                 — документация
├── src/
│   ├── main.cpp          — точка входа
│   ├── server/           — HTTP-сервер и маршрутизация
│   ├── db/               — работа с PostgreSQL
│   ├── models/           — сущности предметной области
│   └── handlers/         — обработчики эндпоинтов
├── web/                  — HTML/CSS/JS
└── tests/                — автотесты
```

## Требования

- Arch Linux / CachyOS (или другая система с Qt6)
- Пакеты: `base-devel`, `cmake`, `ninja`, `gcc`, `qt6-base`, `qt6-httpserver`, `postgresql-libs`

## Локальная проверка

```bash
make setup     # конфигурация CMake
make build     # сборка
make run       # запуск сервера
make test      # автотесты (пока не настроены)
make clean     # очистка сборки
```

## Конфигурация

Скопируйте `.env.example` в `.env` и заполните значения:

```bash
cp .env.example .env
```

Сам `.env` в репозиторий не попадает.

## Healthcheck

После запуска:

```bash
curl http://localhost:8080/health
```

Ожидаемый ответ:

```json
{"service":"auctionhub","status":"ok"}
```

## Правила внесения изменений

### Обязательные команды проверки

Перед каждым коммитом и перед открытием запроса на слияние необходимо
локально выполнить:

```bash
make setup     # конфигурация сборки
make build     # сборка проекта
make test      # автотесты
make quality   # форматирование и статический анализ
make verify    # полный набор локальных проверок
```

Команда `make verify` объединяет остальные и должна завершаться успешно.
Если хотя бы один шаг падает — изменение не готово к слиянию.

### Запрещённые действия

- Удалять или отключать тесты, чтобы пройти проверку.
- Снижать пороги качества, отключать анализаторы (`clang-tidy`,
  `clang-format`) или ослаблять CI.
- Коммитить файл `.env` с реальными секретами.
- Коммитить локальные файлы, каталоги сборки (`build/`) и артефакты
  компиляции (`*.o`, `*.so`, `*.exe`).
- Изменять файлы критической конфигурации приёмки без отдельного
  согласования и отражения в запросе на слияние.
- Вносить изменения напрямую в основную ветку (`main`) в обход
  запроса на слияние.

### Порядок приёмки

1. Задача оформляется отдельно (issue или запись в трекере).
2. Изменение выполняется в отдельной ветке.
3. Все обязательные команды проверки выполняются локально и успешно.
4. Изменение попадает в удалённый репозиторий через запрос на слияние.
5. Запрос на слияние проходит проверку (в том числе CI, когда он появится).
6. После слияния изменение считается принятым.

Приёмка работы преподавателем проводится в форме живой демонстрации:
показывается путь изменения от задачи до тега версии, объясняются
правила внесения изменений, выполняется контрольное изменение через
ветку и запрос на слияние.
